Oxide Bot Monitor — Centralized Bot Monitoring & Order Tracking

ระบบศูนย์กลางสำหรับดูสถานะและสั่งงานบอทเติมเกมหลายเครื่องพร้อมกัน พร้อม State Machine ติดตามออเดอร์
ทำด้วย NestJS + TypeScript, PostgreSQL และ WebSocket

1. ขั้นตอนการติดตั้งและรันระบบ

สิ่งที่ต้องติดตั้งก่อน: Node.js 20 ขึ้นไป, pnpm และ Docker (ใช้รัน PostgreSQL)

ขั้นตอน

1. ติดตั้ง Dependencies
   pnpm install

2. สร้างไฟล์ .env จากตัวอย่าง

   cp .env.example .env # Windows PowerShell: Copy-Item .env.example .env

   ค่าในไฟล์ตัวอย่างใช้ได้ทันทีสำหรับเครื่อง Local ถ้าจะใช้งานจริง ควรเปลี่ยน ADMIN_TOKEN กับ AGENT_TOKEN เป็นค่าของตัวเอง

3. เปิด PostgreSQL
   pnpm db:up

   คำสั่งนี้รัน docker compose up -d postgres จาก Candidate Pack ฐานข้อมูลจะอยู่ที่ localhost:55432

4. Build โปรเจกต์
   pnpm build

   ต้อง Build ก่อนรัน Migration เพราะสคริปต์ Migration ทำงานจากไฟล์ที่คอมไพล์แล้วในโฟลเดอร์ dist/

5. สร้างตารางในฐานข้อมูล
   pnpm db:migrate

   สคริปต์จะรัน db/schema.sql และ db/seed.sql ของ Candidate Pack ตามด้วยไฟล์ใน db/migrations/ (002, 003) ตามลำดับ ไฟล์ต้นฉบับของ Pack คงไว้ตามเดิมทั้งหมด ส่วนที่โจทย์กำหนดเพิ่มเติมแยกไว้เป็น Migration ต่างหาก ได้แก่สถานะออเดอร์ตามโจทย์, Kill-switch, แพ็กเกจโค้ด และ Idempotency Key คำสั่งนี้รันซ้ำได้ Migration ที่รันไปแล้วจะถูกข้าม

6. เปิดเซิร์ฟเวอร์
   pnpm start

   ตอนเริ่ม เซิร์ฟเวอร์จะตรวจว่าต่อฐานข้อมูลได้และ Migration ครบ ถ้าไม่ครบจะหยุดทันทีพร้อมบอกว่าต้องรันคำสั่งอะไร

7. เปิดบอท (เปิด Terminal ใหม่)
   pnpm agents

   คำสั่งนี้เปิด bot-01, bot-02 และ bot-03 เป็น Process แยกกัน แทนเครื่อง Notebook 3 เครื่อง ถ้าปิด Terminal นี้ก็เท่ากับเครื่องดับจริง ถ้าต้องการ Bot Simulator ของ Pack ด้วย ให้รัน pnpm simulator อีกหน้าต่าง ระบบจะส่งคำสั่งไปที่ Simulator เมื่อบอทตัวนั้นไม่มีการเชื่อมต่อ WebSocket

8. เข้า Dashboard
   - เปิด http://localhost:3001
   - ใส่ค่า DMIN_TOKEN จากไฟล์ .env หรือเปิด http://localhost:3001/#token=<ADMIN_TOKEN> ตรงๆ
   - กดปุ่ม "+ 5 ออเดอร์ (ชำระแล้ว)" แล้วดูบอทรับงาน การ์ดของแต่ละเครื่องและแถบสรุปจะอัปเดตเองแบบ Real-time

9. รัน Test
   pnpm test
   pnpm test:e2e

   Integration Test สร้างฐานข้อมูลแยกชื่อ oxide_monitor_test เอง จึงไม่ไปยุ่งกับข้อมูลที่ใช้อยู่ ส่วนการยิง API ด้วยมือ ใช้ไฟล์ [http/api.http](http/api.http) ได้ (รองรับ VS Code REST Client และ JetBrains) แค่ตั้ง @token ให้ตรงกับ .env

10. ลองจำลองปัญหาเอง
    - pnpm agent bot-01 --fail-rate 0.6 — บอททำงานพลาดบ่อย ใช้ดูการ Retry และ Backoff ใน Timeline ของออเดอร์
    - pnpm agent bot-03 --freeze-after 10 — บอทค้าง: การเชื่อมต่อยังเปิดอยู่แต่หยุดส่ง Heartbeat
    - ปิด Terminal ของบอทระหว่างที่กำลังทำงาน — ออเดอร์จะเปลี่ยนเป็น DELAYED แล้วบอทตัวอื่นรับงานต่อ
    - กด "ปิดทั้งระบบ" บน Dashboard — งานที่ทำอยู่จะทำต่อจนจบ แต่จะไม่มีงานใหม่ถูกแจกออกไป

11. ถ้าเจอปัญหาตอนรัน
    - เซิร์ฟเวอร์หยุดพร้อมข้อความ Cannot reach PostgreSQL — Container ยังไม่ขึ้น ให้เช็คด้วย docker compose ps
    - บอทถูกตัดด้วยรหัส 4401 — AGENT_TOKEN ของบอทกับเซิร์ฟเวอร์ไม่ตรงกัน

2. วิธีแก้เคสปัญหา

ส่วนนี้ครอบคลุม 5 เคสหลักที่ระบบลักษณะนี้พบบ่อยและก่อให้เกิดความเสียหายจริงหากจัดการผิดพลาด นอกจากนี้ได้ทดสอบการใช้งานในรูปแบบที่ไม่ถูกต้อง (กดซ้ำต่อเนื่อง, ผู้ใช้หลายคนสั่งงานพร้อมกัน, ปิดบอทระหว่างทำงาน, ส่งข้อมูลผิดรูปแบบ) และแก้ไขปัญหาที่พบเพิ่มเติม ทุกข้อมี Test ที่รันกับ PostgreSQL จริงอยู่ใน test/e2e/

หลักที่ใช้กับทุกเคสคือ ให้ฐานข้อมูลเป็นคนตัดสินว่าใครได้ก่อน
การเปลี่ยนสถานะออเดอร์ทุกครั้งทำใน Transaction เดียว ใช้ Row Lock ของ PostgreSQL และเขียนแบบ Compare-and-Set (UPDATE ... WHERE status = <สถานะที่คาดไว้>) ถ้ามีคนอื่นเปลี่ยนไปก่อน คำสั่งจะไม่มีผลและไม่ทับข้อมูลกัน ทุกการเปลี่ยนสถานะยังถูกบันทึกลง order_events ใน Transaction เดียวกัน จึงย้อนดู Timeline ได้เสมอว่าเกิดอะไรขึ้น เพราะอะไร และบอทตัวไหนทำ

เคสที่ 1: ส่งคำขอซ้ำ (Idempotency)

ปัญหา: ลูกค้ากดปุ่มรัว, Client ส่งซ้ำหลัง Timeout หรือ Payment Webhook ยิงมาสองรอบ ถ้าไม่กันไว้ จะได้ออเดอร์ซ้ำหรือออเดอร์ถูกส่งเข้าคิวสองครั้ง

วิธีแก้:

1. Idempotency-Key — การสร้างออเดอร์ต้องส่ง Header Idempotency-Key มาด้วย ระบบจะจองคีย์ด้วย INSERT ... ON CONFLICT ซึ่งเป็นคำสั่งเดียวแบบ Atomic
   - ส่งคีย์เดิมกับ Body เดิมซ้ำ: ได้ Response เดิมกลับไป พร้อม Header Idempotent-Replayed: true
   - ส่งคีย์เดิมแต่ Body ต่าง: ได้ 422
   - คำขอแรกยังทำไม่เสร็จ: ได้ 409 พร้อม Retry-After
2. Hash แบบไม่สนลำดับ key — Body ถูกเรียง key ก่อน Hash ดังนั้น {"a":1,"b":2} กับ {"b":2,"a":1} นับเป็นคำขอเดียวกัน
3. คีย์ไม่ค้างถ้าเซิร์ฟเวอร์ล่มกลางทาง — คีย์ที่ค้างสถานะ processing เกิน 60 วินาทีจะถูกคำขอถัดไปรับช่วงต่อ ไม่ต้องรอหมดอายุ 24 ชั่วโมง
4. กันซ้ำด้วย externalOrderId ด้วย — คอลัมน์นี้เป็น UNIQUE ดังนั้นต่อให้ Client เปลี่ยนคีย์ใหม่ ก็จะไม่มีออเดอร์ซ้ำ ระบบตอบ 200 พร้อม created: false แต่ถ้าส่ง ID เดิมพร้อมยอดเงินหรือสินค้าที่ไม่ตรงกับของเดิม แปลว่า Client มีบั๊ก ระบบจะตอบ 409 ORDER_CONFLICT และบอกว่า field ไหนไม่ตรง (เทียบเฉพาะ field ที่ส่งมา)
5. ยืนยันการชำระเงินซ้ำได้โดยไม่มีผลเพิ่ม — การเปลี่ยน PENDING_PAYMENT → QUEUED เป็น Compare-and-Set ครั้งที่สองจึงได้ changed: false และไม่มี Event ซ้ำ

ทดสอบ: ยิง 20 คำขอพร้อมกันด้วยคีย์เดียวกัน ได้ออเดอร์เดียว และกดยืนยันชำระ 20 ครั้งพร้อมกัน ได้ Event QUEUED ครั้งเดียว (01-idempotency, 07-regressions)

เคสที่ 2: บอทหลายตัวแย่งงานพร้อมกัน (Concurrency)

ปัญหา: บอทหลายเครื่องขอรับงานพร้อมกัน ถ้าไม่ระวัง ออเดอร์เดียวจะถูกแจกให้สองเครื่อง และลูกค้าได้ของสองรอบ

วิธีแก้: การรับงาน (claimNext) ทำใน Transaction เดียวตามลำดับนี้

1. อ่านค่า Kill-switch แบบ FOR SHARE (รายละเอียดอยู่ในเคสที่ 5)
2. Lock แถวของบอทด้วย FOR UPDATE บอทตัวเดียวจึงขอรับงานซ้อนกันสองครั้งไม่ได้
3. เช็คว่าบอทยังไม่มีงานที่ทำค้างอยู่
4. เลือกออเดอร์ด้วย FOR UPDATE SKIP LOCKED แถวที่มีบอทอื่นจับอยู่จะถูกข้ามไปเลย ไม่ต้องรอกัน บอทแต่ละตัวจึงได้คนละออเดอร์และไม่ติดคอขวด
5. เปลี่ยนเป็น IN_PROGRESS และเพิ่มค่า attempt_count

กันอีกชั้นที่ฐานข้อมูล: มี Unique Index uq_orders_one_active_per_bot บังคับว่าบอทหนึ่งตัวถืองานได้ไม่เกินหนึ่งงาน ต่อให้โค้ดมีบั๊ก ฐานข้อมูลก็จะไม่ยอม

ทดสอบ: บอท 10 ตัว ตัวละ 5 คำขอพร้อมกัน แย่งออเดอร์ 6 รายการ ได้งานครบ 6 ไม่มีซ้ำ ลอง Load จริงกับ 200 ออเดอร์ บอท 3 ตัวทำเสร็จครบโดยไม่มีออเดอร์ไหนถูกแจกซ้ำ (02-concurrent-dispatch)

เคสที่ 3: เครื่องบอทหลุดหรือค้างระหว่างทำงาน (Heartbeat Timeout)

ปัญหา: เครื่องดับ, เน็ตหลุด หรือโปรแกรมค้างโดยที่ยังเชื่อมต่ออยู่ ถ้าไม่จัดการ ออเดอร์จะค้างที่ IN_PROGRESS ตลอดไป

วิธีแก้: มี Monitor วนตรวจทุก 2 วินาที

1. บอทเงียบนานเกิน HEARTBEAT_TIMEOUT_MS (10 วินาที) — ถือว่า Offline และเซิร์ฟเวอร์ตัดการเชื่อมต่อด้วยรหัส 4408 ถ้า Socket หลุดเอง (เช่น Process ตาย) จะเป็น Offline ทันที
2. ออเดอร์ของบอทที่ Offline — เปลี่ยนเป็น DELAYED ก่อน ยังไม่ตัดสินว่าล้มเหลว เพราะเน็ตหลุดแป๊บเดียวไม่ควรทำให้ต้องเริ่มงานใหม่
3. DELAYED นานเกิน ORDER_REQUEUE_AFTER_MS (20 วินาที) — ส่งกลับเข้าคิวให้บอทอื่นทำ หรือเป็น FAILED ถ้าครบจำนวนครั้งแล้ว
4. บอทต่อกลับมา — บอทจะบอกในข้อความ hello ว่าตัวเองถืองานอะไรอยู่
   - ถ้าเป็นงานเดิมและ attempt ตรงกัน ทำต่อได้เลย (DELAYED → IN_PROGRESS)
   - ถ้าโปรแกรมรีสตาร์ทจนงานหาย ส่งกลับเข้าคิวทันทีโดยไม่ต้องรอ Timeout
   - ถ้างานถูกส่งให้บอทอื่นไปแล้ว บอกให้บอทตัวนี้ทิ้งงานนั้น
5. บอทยังส่ง Heartbeat แต่งานไม่เสร็จสักที — ออเดอร์ที่อยู่ใน IN_PROGRESS นานเกิน ORDER_MAX_PROCESSING_MS (5 นาที) จะถูกดึงกลับไปลองใหม่ และเซิร์ฟเวอร์ส่ง order.revoked ให้บอทหยุดทำ
6. ไม่ส่งงานกลับไปหาบอทตัวเดิมที่เพิ่งพลาด — จากการทดสอบกับบอทจริง พบว่างานที่ Timeout วนกลับไปหาบอทตัวเดิมที่ค้างอยู่ถึง 3 รอบจนกลายเป็น FAILED ทั้งที่มีบอทอื่นว่าง จึงเพิ่มคอลัมน์ last_bot_id ให้บอทอื่นได้สิทธิ์ก่อน RETRY_SAME_BOT_AFTER_MS (10 วินาที) ถ้าไม่มีบอทอื่นเลย บอทเดิมก็รับต่อได้ งานจึงไม่ค้าง

ทุก Query ของ Monitor ใช้ SKIP LOCKED ถึงจะรัน Monitor หลายตัวพร้อมกันก็ไม่ทำงานซ้ำกัน

ทดสอบ: มีใน 03-heartbeat-timeout และลองกับระบบจริงแล้ว: Kill บอทกลางงาน บอทอื่นทำต่อจนเสร็จ, Kill เซิร์ฟเวอร์ระหว่างทำงาน บอทต่อกลับเองและออเดอร์เสร็จครบ, บอทค้าง ถูกตัดแล้วกลับมาทำงานต่อได้

เคสที่ 4: งานล้มเหลว รายงานซ้ำ หรือรายงานมาช้า (Retry)

ปัญหา: งานพลาดชั่วคราว (Captcha, Provider ไม่ตอบ), รายงานผลถูกส่งซ้ำเพราะเน็ต หรือบอทที่หลุดไปแล้วกลับมารายงานผลของงานเก่า

วิธีแก้:

1. ลองใหม่แบบ Exponential Backoff — งานที่พลาดแบบลองใหม่ได้จะกลับเข้าคิว โดยกำหนดเวลาที่หยิบได้ครั้งถัดไปเป็น 2s → 4s → 8s ... (สูงสุด 60 วินาที) ครบ max_attempts แล้วเป็น FAILED ถ้าเป็นความผิดพลาดที่ลองใหม่ไม่ได้ ก็เป็น FAILED ทันที และผู้ดูแลกด Retry เองได้
2. รายงานผลไม่หาย — บอทเก็บรายงานไว้ใน Outbox และส่งซ้ำจนกว่าเซิร์ฟเวอร์จะตอบรับ (At-least-once) เซิร์ฟเวอร์จึงต้องรับรายงานซ้ำได้โดยไม่มีผลซ้ำ ทั้งรายงานสำเร็จและรายงานล้มเหลวที่ส่งซ้ำจะได้ ok: true, duplicate: true โดยไม่เปลี่ยนข้อมูลอีก
3. attempt_count ทำหน้าที่เป็น Fencing Token — ค่านี้เพิ่มทุกครั้งที่มีบอทรับงาน และไม่เคยถูกรีเซ็ต บอทต้องส่งค่า attempt กลับมาพร้อมผล ถ้าเป็นผลของรอบเก่าที่มีบอทอื่นรับต่อไปแล้ว ระบบจะปฏิเสธ (STALE_ATTEMPT) รายงานจากบอทที่ไม่ได้ถืองานจึงทับงานของบอทตัวจริงไม่ได้
4. ผลสำเร็จที่มาช้ายังรับได้ ถ้ายังไม่มีใครทำต่อ — ถ้าระบบส่งงานกลับเข้าคิวไปแล้ว (เพราะบอทหลุดหรือ Timeout) แต่บอทตัวเดิมกลับมาบอกว่าเติมสำเร็จ และยังไม่มีบอทอื่นรับงานนั้น ระบบจะยอมรับผลและปิดเป็น COMPLETED เพราะลูกค้าได้ของไปแล้วจริง ถ้าส่งไปให้บอทอื่นทำซ้ำ จะกลายเป็นเติมให้สองครั้ง
5. คำสั่งควบคุมบอทไม่หาย — คำสั่งมีสถานะ queued → running → success | failed
   - ถ้าบอทออฟไลน์ คำสั่งรอในคิวและถูกส่งใหม่ตอนบอทต่อกลับมา บอทกันการทำซ้ำด้วยรหัสคำสั่ง
   - คำสั่งที่บอทไม่ตอบภายใน COMMAND_TIMEOUT_MS ถือว่าล้มเหลว
   - ถ้าไม่มีบอทต่ออยู่ คำสั่ง start / stop / restart / status จะส่งไป Bot Simulator แทน โดยลองใหม่ 3 ครั้งเมื่อเจอ Network Error หรือ 5xx
6. บอทต่อใหม่แบบ Backoff + Jitter — ตอนเซิร์ฟเวอร์รีสตาร์ท บอททุกตัวจะไม่รุมต่อเข้ามาพร้อมกัน

ทดสอบ: 04-retry และ 07-regressions รวมถึงกรณีรายงานผลชนกับ Timeout 15 รอบ ออเดอร์จบที่ COMPLETED ทุกรอบ ไม่มีรอบไหนที่งานถูกส่งไปทำซ้ำ

เคสที่ 5: กด Kill-switch ตอนบอทกำลังรับงาน

ปัญหา: ผู้ดูแลกด "ปิดทั้งระบบ" ในจังหวะเดียวกับที่บอทกำลังรับงาน ถ้าเช็คค่าแล้วค่อยรับงานแยกกันสองจังหวะ อาจมีงานหลุดออกไปหลังกดปิดแล้ว

วิธีแก้:

1. ใช้ Lock คั่นจังหวะ — ตอนรับงาน ระบบอ่านค่า Kill-switch ด้วย FOR SHARE ส่วนการกดปิดเป็นคำสั่ง UPDATE ซึ่งต้องรอให้ Transaction รับงานที่กำลังทำอยู่จบก่อน การรับงานที่เริ่มหลังจากกดปิดไปแล้วจะเห็นค่าใหม่แน่นอน จึงไม่มีช่องว่างให้งานหลุด
2. บอกบอทด้วย — เซิร์ฟเวอร์ส่ง system.killSwitch ไปที่บอททุกตัวให้หยุดขอรับงานทันที เป็นการกันชั้นที่สอง
3. งานที่ทำอยู่ให้ทำจนจบ — ถ้าหยุดกลางคัน ลูกค้าอาจโดนตัดเงินแต่ไม่ได้ของ
4. ปิดบอทรายเครื่องมีผลทันที — ระบบบันทึก enabled = false ลงฐานข้อมูลตั้งแต่ตอนสั่ง จึงไม่แจกงานให้เครื่องนั้นอีก แม้คำสั่งยังส่งไปไม่ถึงตัวบอท
5. หลายคนกดพร้อมกันได้ — การเปลี่ยนค่า Lock แถวด้วย FOR UPDATE คำขอจึงเรียงกันทีละคำขอ ถ้ากดค่าเดิมซ้ำจะไม่มีผล (ไม่เขียนข้อมูลและไม่ลง Audit Log ซ้ำ) และบรรทัดสุดท้ายของ Audit Log ตรงกับสถานะจริงเสมอ

ทดสอบ: จำลอง Transaction ที่ถือ Lock ค้างไว้ แล้วดูว่าการกดปิดต้องรอจริง และหลังกดปิดไม่มีบอทไหนรับงานได้ (05-kill-switch)

เคสเพิ่มเติมที่พบจากการทดสอบการใช้งานผิดรูปแบบ

ได้ทดสอบการใช้งานผิดรูปแบบรวมกว่า 200 กรณี ทั้งการกรอกข้อมูลไม่ถูกต้อง การกดซ้ำต่อเนื่อง การสั่งงานพร้อมกันจากผู้ใช้หลายคน และการส่งข้อมูลผิดรูปแบบจากบอท ปัญหาที่พบและได้รับการแก้ไขแล้วมีดังนี้ (Test อยู่ใน 07-regressions)

1. ยกเลิกออเดอร์ที่บอทอาจเติมไปแล้ว — บอทหลุด ออเดอร์กลับเข้าคิว ผู้ดูแลกดยกเลิก แล้วบอทกลับมาบอกว่าเติมสำเร็จ ผลคือออเดอร์ถูกยกเลิกทั้งที่ลูกค้าได้ของไปแล้ว ตอนนี้จึงยกเลิกได้เฉพาะออเดอร์ที่ยังไม่เคยมีบอทรับ ถ้าเคยมีบอทรับแล้วจะได้ 409 ORDER_ALREADY_ATTEMPTED และ Dashboard จะซ่อนปุ่มยกเลิก
2. อัปโหลดแพ็กโค้ดไฟล์เดียวกันพร้อมกันแล้วได้ 500 — เพราะทุกคำขอใช้ไฟล์ชั่วคราวชื่อเดียวกัน แก้ให้แต่ละคำขอใช้ชื่อไม่ซ้ำกัน
3. กด "อัปเดตโค้ด" รัว หรือสลับแพ็ก A → B → A — เคยได้คำสั่งอัปเดตค้างหลายตัว และเครื่องจบที่แพ็กผิด ตอนนี้คำสั่งใหม่จะแทนที่คำสั่งเก่าที่ยังค้าง บอทติดตั้งทีละแพ็ก และ Heartbeat รายงานเวอร์ชันที่ติดตั้งจริงบนเครื่องกลับมาด้วย
4. ไฟล์แพ็กหายจาก Disk (Hosting หลายเจ้าล้าง Disk ตอน Redeploy) — ดาวน์โหลดจะได้ 410 PACKAGE_FILE_MISSING และแค่อัปโหลดไฟล์เดิมซ้ำก็กู้คืนได้
5. ข้อมูลผิดรูปแบบ — ID ยาวเกินช่วง, 1e3, อักขระ NUL, amount: 0, สกุลเงินที่ไม่รองรับ, offset ที่มีค่าสูงผิดปกติ จากเดิมที่บางตัวได้ 500 ตอนนี้ได้ 400 พร้อมบอกว่าผิดตรงไหน
6. บอทส่ง hello ซ้ำ หรือส่งข้อความใหญ่มาก — ระบบรับ hello แค่ครั้งเดียวต่อการเชื่อมต่อ และจำกัดขนาดข้อความไว้ที่ 256KB

ข้อจำกัดที่ทราบ และเหตุผล

1. มีความเสี่ยงเติมซ้ำในกรณีเดียว — ถ้าบอทหลุดนาน งานถูกส่งให้บอทอื่น และ บอทอื่นรับงานไปแล้ว แล้วบอทตัวแรกกลับมาบอกว่าเติมสำเร็จ จะเกิดการเติมซ้ำ กรณีนี้ไม่สามารถแก้ไขได้ทั้งหมดจากฝั่ง Central ระบบจริงควรส่ง orderId + attempt เป็น Idempotency Key ไปที่ผู้ให้บริการเติมเกมด้วย ทั้งนี้ สถานะ DELAYED ที่คั่นไว้ก่อนส่งงานกลับเข้าคิวช่วยลดโอกาสเกิดกรณีนี้ได้มาก
2. รองรับการรันเซิร์ฟเวอร์เพียงตัวเดียว — การแจกงานและ Monitor ถูกต้องอยู่แล้ว เพราะใช้ Lock ของฐานข้อมูล แต่รายการบอทที่ต่อ WebSocket อยู่เก็บในหน่วยความจำของแต่ละเครื่อง ถ้าจะขยายเป็นหลายตัว ต้องใช้ PostgreSQL LISTEN/NOTIFY หรือ Redis Pub/Sub ช่วยกระจายคำสั่ง
